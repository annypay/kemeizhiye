# 会议纪要 — 会议包编制规范与流程

> 本目录存放经总经办确认签发的董事长周例会会议纪要。每期纪要以一套“会议包”管理：临时区负责转录、整理和确认，正式区只保留三版当前权威纪要及其 Word 打印稿。

---

## 一、术语与单一来源

会议日期、汇报统计期和归档周期不能互相替代。Agent 必须读取元数据和来源文件，不能从附件的随意文件名猜测日期或周期。

| 字段 | 含义与格式 | 权威来源 | 使用位置 |
| --- | --- | --- | --- |
| `meeting_date` | 会议实际发生日期，`YYYY-MM-DD` | 会议录音目录、会议通知或人工转录 | 纪要头部、纪要编号 |
| `archive_week` | 会议日期所在自然周的周一至周日，`YYYYMMDD-YYYYMMDD` | 由 `meeting_date` 计算 | 临时包、汇报目录、纪要目录及文件前缀 |
| `report_period` | 汇报材料覆盖的统计区间，`YYYY-MM-DD/YYYY-MM-DD` | 总经办汇总表或汇报正文 | 元数据，仅作事实溯源 |
| `plan_period` | 汇总表中重点计划的执行区间，`YYYY-MM-DD/YYYY-MM-DD` | 总经办汇总表或计划正文 | 元数据，仅作事实溯源 |
| `report_cutoff` | 汇总统计截止日，`YYYY-MM-DD` | 总经办汇总表 | 元数据，仅作事实溯源 |
| `signed_at` | 实际签发日期，`YYYY-MM-DD` | 签发确认记录 | 正式纪要文末落款、Word 打印稿 |
| `summary_source` | 总经办汇总表的仓库相对路径 | 实际文件 | 元数据 |
| `roster_source` | 周例会名单的仓库相对路径 | 实际文件 | 元数据 |
| `audio_source` | 录音文件或录音目录的仓库相对路径 | 实际文件 | 元数据 |
| `transcript_source` | 人工转录草稿或归档转录底稿的仓库相对路径 | 实际文件 | 元数据 |
| `draft_created_at` | 草稿创建日期，`YYYY-MM-DD` | 创建人/脚手架 | 临时草稿元数据 |

**归档周期计算**：会议日所在周以周一开始、周日结束。会议日期为 2026-08-25 时，归档周期为 `20260824-20260830`；会议日期为 2026-08-31 时，归档周期为 `20260831-20260906`。会议录音仍按实际会议日期保存，例如 `会议录音/2026-08-31/`，它不是归档周期目录。

每份转录草稿、三版纪要和待确认事项清单的文件开头必须有以下机器元数据。值尚未确认时写 `pending`，不得虚构。该注释会被 Word 生成脚本忽略，不会出现在打印稿中。

```markdown
<!-- MEETING-MINUTES-META
meeting_date: 2026-08-31
archive_week: 20260831-20260906
report_period: pending
plan_period: pending
report_cutoff: pending
summary_source: pending
roster_source: pending
audio_source: pending
transcript_source: 00-临时存放/会议纪要/20260831-20260906/20260831-20260906-董事长例会-转录草稿【待编辑】.md
draft_created_at: 2026-08-31
signed_at: pending
-->
```

同一会议包的三版纪要和待确认事项清单必须使用完全相同的前十项元数据。`signed_at` 独立于 `meeting_date`：临时草稿可为 `pending`，正式纪要必须为已确认的实际签发日期，并与三版 Markdown、Word 文末落款一致。`JK-HY-YYYYMMDD` 中的日期必须等于 `meeting_date`。

## 二、临时会议包与正式入库

### 2.1 创建临时会议包

会议结束后先按会议实际日期创建临时包：

```powershell
& "C:\Program Files\nodejs\node.exe" scripts/create_meeting_package.js 2026-08-31
```

如已掌握汇总、名单或录音来源，可在创建时附带仓库相对路径：

```powershell
& "C:\Program Files\nodejs\node.exe" scripts/create_meeting_package.js 2026-08-31 `
  --report-period 2026-08-24/2026-08-30 `
  --plan-period 2026-09-01/2026-09-07 `
  --report-cutoff 2026-08-31 `
  --summary-source "03-例会汇报/董事长例会/各专业汇报内容/20260831-20260906/20260831-20260906-总经办-汇总.xlsx" `
  --roster-source "03-例会汇报/董事长例会/周例会名单/20260831-20260906-周例会名单.xlsx" `
  --audio-source "03-例会汇报/董事长例会/会议录音/2026-08-31/"
```

脚本会创建且只会创建一个新的临时目录，已有同周期目录时拒绝覆盖：

```text
00-临时存放/会议纪要/20260831-20260906/
├─ 20260831-20260906-董事长例会-转录草稿【待编辑】.md
├─ 20260831-20260906-董事长例会纪要-董事长版【待确认】.md/.docx
├─ 20260831-20260906-董事长例会纪要-总经理版【待确认】.md/.docx
├─ 20260831-20260906-董事长例会纪要-完整版（群发）【待确认】.md/.docx
└─ 20260831-20260906-董事长例会-待确认事项【待确认】.md
```

第一项由脚手架生成。其余文件由 Agent 依据转录和输入材料生成，不能以空白模板代替会议事实。临时区文件不自动提交。

### 2.2 输入清点与生成顺序

1. 记录转录草稿、总经办汇总、各专业汇报、周例会名单、会议录音和未关闭工作事项的实际路径；缺件在待确认事项清单中列缺口，不得补写内容。
2. 以详细董事长版为唯一事实和结构主源，先完成其时间节点表、讲话、重点工作和跟踪事项。
3. 从董事长版筛选、合并和精简，生成总经理版和群发版；同一节点、决策和指示不得改变事实口径。
4. 签发前将 `signed_at` 写为实际签发日；三版文末签发日期必须同步，不能默认使用或复制 `meeting_date`。
5. 用指定脚本生成三份同名 Word 打印稿。生成前检查同名 `.docx` 和 `~$` Office 锁文件；任何已手改的 Word 终稿优先于 Markdown，必须先回写 Markdown，不能以 `--force` 覆盖。
6. 总经办确认三版和事项处理口径后，再由 `/doc-intake` 移入正式目录、去除状态标记，并由 `/work-tracker` 处理已确认事项。

### 2.3 正式入库后的边界

正式目录格式如下：

```text
03-例会汇报/董事长例会/会议纪要/20260831-20260906/
├─ 20260831-20260906-董事长例会纪要-董事长版.md/.docx
├─ 20260831-20260906-董事长例会纪要-总经理版.md/.docx
└─ 20260831-20260906-董事长例会纪要-完整版（群发）.md/.docx
```

转录底稿移入 `_archive/会议纪要/<归档周期>/`。待确认事项清单在事项已被确认、登记或明确不纳入台账后再归档；它不能进入正式纪要目录，也不能据此自动新增、关闭或处罚 `JK-RW` 事项。

## 三、三版纪要范式

### 3.1 董事长版：唯一主源

董事长版按以下顺序编制；带“适用时”的章节只有存在可定位事实时才出现。

1. `一、会议信息`：两列表 `项目 | 内容`，至少包含会议名称、会议时间、主持人、出席人员、记录/整理。未知信息写“待补充”。
2. `二、重点工作时间节点`：三列表 `节点日期 | 事项 | 责任部门`，按节点日期升序排列。若来源只有倒计时、工期或“待明确”，表头改为 `节点/时限 | 事项 | 责任部门`；未定日期/时限的条目排在有日期条目之后。
3. `三、本周重点决策` 或 `三、本周重点工作`：仅保留转录或汇总中明确的会议决定、部署或重点工作，不把推测写成决策。
4. `四、董事长指示与要求`：逐项提炼董事长讲话，保留范围、条件和原有强度，不擅自增加处罚、责任或期限。
5. `五、总经理要求`：逐项提炼总经理讲话。
6. `六、关联未关闭事项复盘`（适用时）：四列表 `事项编号 | 关联内容 | 当前状态 | 本次会议关注`；表后声明它仅作复盘，不代表完成、关闭或新增处罚。
7. `六、跟踪事项` 或 `七、跟踪事项`：四列表 `序号 | 事项 | 时间节点 | 责任`。责任或期限尚未明确时填写“待明确”，并同步列入待确认事项清单。

历史 [20260824830 董事长版](20260824830/2026824830-董事长例会纪要-董事长版.md) 的三列表节点表是版式基准。新期不得再用无分隔的 `2026824830`、`2026831906` 等短串代替归档周期。

### 3.2 总经理版：三列节点的精简视图

总经理版固定为以下四节：

1. `一、关键时间节点`：三列表 `时间 | 事项 | 责任`，逐行来自董事长版的节点表，可压缩表述但不改变日期、责任或状态。
2. `二、本周重点决策` 或 `二、重点工作安排`：来自董事长版的重点决策/重点工作和需总经理统筹的跟踪事项。
3. `三、董事长指示要点`：保留战略性、跨部门和时间敏感要求；执行细节可合并。
4. `四、总经理要求`：保留计划、汇报、协同和管理类核心要求。

总经理版不含会议信息表、未关闭事项复盘表和跟踪事项表。

### 3.3 完整版（群发）：两列节点的精简视图

群发版固定为以下四节：

1. `一、董事长讲话核心`；
2. `二、总经理讲话核心`；
3. `三、重点工作时间节点`：两列表 `时间 | 事项`，逐行来自董事长版节点表，删除责任列；
4. `四、本周重点决策` 或 `四、本周重点工作`：来自董事长版已明确的决策、部署和跟踪重点。

群发版不包含会议信息表、责任列、未关闭事项编号或待确认事项。语言应精炼，不公开未核实的责任归属、期限或处罚结论。

## 四、命名与版式

### 4.1 名称规则

| 文档 | 临时区名称 | 正式区名称 |
| --- | --- | --- |
| 转录草稿 | `<归档周期>-董事长例会-转录草稿【待编辑】.md` | 归档至 `_archive/会议纪要/<归档周期>/` |
| 董事长版 | `<归档周期>-董事长例会纪要-董事长版【待确认】.md/.docx` | `<归档周期>-董事长例会纪要-董事长版.md/.docx` |
| 总经理版 | `<归档周期>-董事长例会纪要-总经理版【待确认】.md/.docx` | `<归档周期>-董事长例会纪要-总经理版.md/.docx` |
| 完整版（群发） | `<归档周期>-董事长例会纪要-完整版（群发）【待确认】.md/.docx` | `<归档周期>-董事长例会纪要-完整版（群发）.md/.docx` |
| 待确认事项 | `<归档周期>-董事长例会-待确认事项【待确认】.md` | 确认处理后归档，不进入正式纪要目录 |

最新版不带版本号；被替换版本移入 `_archive/`，用 `-v2`、`-v3` 紧贴扩展名前标识。历史目录和文件不批量重命名；需要关联时，在元数据中保留其实际路径。

### 4.2 Markdown 与 Word 排版

- 每份纪要使用一个 `#` 标题、`##` 章节标题；不使用四级及以下标题。
- 面向阅读者的元数据使用 `>` 引用行；节点说明、倒计时和复盘边界也使用引用行。倒计时汇总行必须整体加粗（`**倒计时：…**`），不得仅加粗“倒计时”标签本身，不得将数字部分留为非加粗。该规则由 `check_meeting_minutes.js` 强制校验。
- 列表统一使用 `1.` 加空格的格式；重点词可使用 `**加粗**`。表格使用标准 Markdown 表格，不使用合并单元格、表内列表、链接、颜色或脚注。
- 会议纪要 Word 固定使用 `20260824830` 目录下《董事长例会纪要-完整版（群发）》的版式合同（`20260824830-group-v1`）：A4 上下 `1200`、左右 `1400` twip；居中黑体 18pt 标题、居中微软雅黑 10pt 副标题、居中仿宋 12pt 会议信息、黑体 14pt 章节、仿宋正文、`D9E2F3` 淡蓝表头与 `999999` 全边框表格，以及右对齐微软雅黑 12pt 签发和日期。Word 不设独立页眉、页脚或页码，签发信息只保留在正文末尾。所有会议纪要表格均使用该表头蓝，不得改为灰色。
- 三版 Markdown 和 Word 均固定使用两行副标题：第一行 `江西柯美纸业有限公司 ｜ 周序号 <archive_week> ｜ <周一日期> ～ <周日月日>`；第二行 `主持人：总经办 ｜ 出席：各专业负责人 ｜ 记录/整理：总经办 ｜ 签发：总经办`。`archive_week` 必须使用标准的 `YYYYMMDD-YYYYMMDD`，不能复用历史无分隔短串。该规则由 `check_meeting_minutes.js` 强制校验。
- 文末签发日期以 `signed_at` 为唯一来源，按实际签发当天填写；它不是会议事实，不得默认等于 `meeting_date`。正式稿三版 Markdown 和 Word 均须使用同一签发日。
- `MEETING-MINUTES-META` 注释不会进入 Word；Markdown 有序列表在 Word 中转为项目符号。版式由 `scripts/test_meeting_minutes.js` 的 DOCX 包结构断言锁定，改动转换器前必须先更新规范、测试与历史标杆说明。
- Word 手工修改后，以手改终稿为准回写 Markdown，再同步其余两版对应内容，防止版本漂移。

## 五、质量门与校验

编制和入库前均运行以下检查：

```powershell
# 临时包：允许来源字段为 pending，但会给出待确认警告
& "C:\Program Files\nodejs\node.exe" scripts/check_meeting_minutes.js "00-临时存放/会议纪要/20260831-20260906" --mode=temporary

# 正式包：必须有三份同源 md/docx，且不允许状态标记文件
& "C:\Program Files\nodejs\node.exe" scripts/check_meeting_minutes.js "03-例会汇报/董事长例会/会议纪要/20260831-20260906" --mode=formal
```

校验器检查周期是否为周一至周日、会议日期是否属于该周期、纪要编号、文件前缀、三版元数据一致性、正式稿签发日期及文末落款、规定章节与表格列数、节点排序、Word 配对、DOCX 文件签名、Word 是否早于 Markdown、来源文件存在性和 `~$` 锁文件。`pending` 产生警告；其中正式稿的 `signed_at` 不得为 `pending`，实际不存在的非 `pending` 来源路径产生错误。

确认入库和提交时，继续执行根目录 README 规定的 `check_repo.js --staged`、台账检查（适用时）和 `gen_index.js`。纪要入库不等于事项已完成；工作事项状态和关闭证据只在工作事项总台账维护。

## 六、历史资料兼容

- 历史周目录和文件名，如 `20260824830`、`2026824830`、`20260819`，保持不动，避免破坏既有链接和 Git 历史。
- 历史 [20260824830](20260824830/) 的三版是当前表格和排版的参照；历史资料不参与新校验器的强制迁移。
- 新建会议包一律遵循本规范。若需为历史会议补充材料，使用实际历史路径作为来源，并在元数据中标记其规范归档周期，不批量重命名原件。
